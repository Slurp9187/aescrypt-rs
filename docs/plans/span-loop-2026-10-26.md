# aescrypt-rs: span loop — read, encrypt or decrypt, MAC and write up to 64 KiB per call

**Status (2026-10-26, UTC):** approved by the owner. Verified at main `ede8f73`
(0.2.0-rc.15). Scope: `encrypt_stream`, the decryption context and trailer, and both
passes of `decrypt_verified`, for v0–v3. Audience: the builder session, the EFV
coordinator (Slurp9187/encrypted-file-vault#1193) and reviewers. The `plan`-labeled
master issue that links here holds status; this doc holds design.

**Built (2026-10-26):** S01–S04 merged in #69 (`18b11c2`), master issue #68. One
design change from review: the 64 KiB spans are a `pub(crate) HeapSpan =
Dynamic<[u8]>` built by `heap_span(len)` from `vec![0u8; len]`, not boxed
`SpanBuffer`s. `Box::new([0u8; N])` builds the array on the stack first, and
secure-gate's `FixedStorage` bound refuses `Fixed<Box<[u8]>>`; `Dynamic<[u8]>` hands
out only `&mut [u8]`, so it cannot grow. The plaintext span is allocated by the
decrypting pass only. Where the text below says `SpanBuffer` for a span, read
`HeapSpan`.

**Follow-up built (2026-10-26): encrypt in one AES backend call per piece, #71.**
`encrypt_block` per 16-byte block paid, on x86, a CPU-feature check and a call into
`aes`'s `#[target_feature(enable = "aes")]` function for every block. `CbcSpan`, a
`cipher::BlockClosure`, runs the CBC loop for each 256-byte piece inside one such call,
in place inside the span wrapper. A compile-time assert keeps `INTERLEAVE` a whole
number of blocks.
- **Experiment:** three alternating rounds of `benches/throughput.rs` encrypt at 64 MiB,
  on one x86 desktop with AES-NI (Ryzen 9 9950X3D), with a ≥10% bar set before
  measuring:
  - per-block, the code before #71: 661 MiB/s;
  - `CbcSpan` per 256 B: 731 MiB/s (+10.5%, kept);
  - `CbcSpan` per whole span: 660 MiB/s.
- **Not measured elsewhere.** On aarch64 without `--cfg aes_armv8`, and on x86 without
  AES-NI, `aes` uses its software backend, which has no dispatch to save.
- **Corrected ratios.** 0.2.0-rc.15 (`6b5a57e`) against #71, back to back on the same
  machine: encrypt about 1.5×, decrypt about 3.5×, `decrypt_verified` about 3×. They
  replace the earlier figures, which mixed runs taken under different machine load.

## Measured state

Read from the code at `ede8f73`. EFV's throughput figures were measured by EFV PERFORMANCE
on a Linux container, not on this workstation; S01 re-measures them here.

- **Encrypt** (`src/encryption/stream.rs:63`, `encrypt_stream`): per 16-byte block, one
  `read_until_full` into a `Block16` (~line 96), a second `Block16` for the XOR output,
  `encrypt_block`, `hmac.update` of 16 bytes (sha2 buffers four of these per compression),
  `write_all` of 16 bytes (~line 119), and two zeroizing drops.
- **Decrypt** (`src/decryption/stream/context.rs`, `cbc_loop`): a 48-byte priming read, then
  per block a 16-byte `read_until_full` (~line 203) into `RingBuffer64`, a copy out of the
  ring into a `Block16`, `decrypt_block`, an XOR into `plaintext_block`, one `write_all` of
  16 bytes (`decrypt_cbc_loop`, ~line 130), and three drops.
- 64 MiB is 4.2 M reads and 4.2 M writes per pass. `decrypt_verified` makes two passes.
- Nothing calls `encrypt_blocks` or `decrypt_blocks`, so the AES-NI backend of `aes` 0.8.4
  (`ParBlocksSize = U8`) never pipelines. `sha2` 0.10.9 dispatches to SHA-NI at runtime.
  This workstation (Ryzen 9 9950X3D) has both.
- EFV measured: encrypt from memory ~400 MiB/s, against ~490 for bulk AES-256-CBC +
  HMAC-SHA256 at 64 KiB; `decrypt_verified` to a null sink ~310 MiB/s; 16-byte writes into
  EFV's `SealedScratch` 27 MiB/s, against 742 MiB/s at 64 KiB; a 64 MiB open end to end
  23 MiB/s.

**Inferred, not yet measured here:** single-thread ceilings of the primitives are CBC
encrypt (serial) ~1.4–1.6 GB/s, CBC decrypt (pipelined) ~8+ GB/s, and HMAC-SHA256 (serial)
~1.8–2.3 GB/s. Run in sequence, that puts the floors at ~0.85 GB/s for encrypt, ~1.5 GB/s
for one-pass decrypt (bound by the HMAC) and ~0.85 GB/s for `decrypt_verified`. The before
and after numbers go in the PR evidence and are copied to the master issue.

## Target model

Both directions read, process and write **up to 64 KiB per call**, with one HMAC update per
span. Decrypt holds back the trailer (32 bytes, or 33 for v1/v2) until EOF under the same
framing rule as today, so the trailer is never decrypted and every error message and length
is unchanged. The wire format is byte-identical. `decrypt_verified` still releases no
plaintext before the tag check and, for v3, the padding check pass. Every buffer that holds
plaintext or a key is wiped on drop (a `Fixed` block or a `Dynamic<[u8]>` span), accessed at Tier 1 only.

### Framing rule, kept exactly

The ring loop decrypts `max(0, floor(T/16) − 2)` blocks of a T-byte payload stream. It
leaves `32 + T mod 16` bytes (or all T bytes when T < 48) for `read_trailer`.

The span loop keeps that rule. After each fill of B buffered bytes, it processes
`floor(B/16) − 2` blocks when that is positive and carries the rest (at most 47 bytes) to the
front. At EOF it does the same once more. Because B ≤ T, processing never runs ahead of the
final answer. Both passes share the one framing function, as they share `cbc_loop` today.

### Encrypt (`src/encryption/stream.rs`)

- `SPAN = 64 * 1024` goes in `src/constants.rs`. The state is one boxed `SpanBuffer<SPAN>`
  and a `Block16` named `prev`, seeded from the session IV wrapper-to-wrapper.
- Each loop iteration:
  1. Call `read_until_full`. A short fill is the final span: apply PKCS#7 to its partial
     block in place. There is always room, since n < SPAN and SPAN is a multiple of 16. An
     empty or 16-aligned input still emits one full pad block, as today.
  2. CBC-encrypt the span in place: XOR in the previous ciphertext block, then
     `encrypt_block`.
  3. One `hmac.update` over the span, then one `write_all`.
  4. Copy the last block into `prev`.
- **Interleave experiment:** encrypt a 256-byte sub-span, then pass it to `hmac.update`, so
  the two serial chains (CBC and SHA) share the CPU's out-of-order window. Keep it only if
  the bench says it is faster; the output bytes are identical either way.

### Decrypt (`src/decryption/stream/context.rs`, rewritten)

Decryption is out of place, between two boxed spans:

- `cipher: SpanBuffer<SPAN + 48>` holds the carry at the front, then the new ciphertext.
- `plain: SpanBuffer<16 + SPAN>` holds the pending plaintext block at `[0..16]`, held back
  for the padding check, and this span's output at `[16..]`.
- The other state:
  - `chain: Block16`, the last processed ciphertext block, which starts as the IV;
  - `chain_before: Block16`, the block before it, used by the v3 final-block check in
    pass 1;
  - `carry_len`, `has_pending` and `blocks`.

For each span where k = `floor(B/16) − 2` is positive:

1. One `hmac.update(&cipher[..16k])`.
2. `decrypt_blocks_inout` over
   `InOutBuf::new(&cipher[..16k], &mut plain[16..16+16k]).into_chunks::<U16>()`. This runs
   the AES-NI 8-block pipeline through the safe API of `aes::cipher::inout`, with no new
   dependency and no `unsafe`.
3. The CBC XOR as a slice loop: `plain[16..32] ^= chain`, then `plain[16+i] ^= cipher[i−16]`.
4. Record `chain` and `chain_before`.
5. One `write_all`: `plain[0..16k]` when a block is pending, otherwise `plain[16..16k]`.
6. Copy the new last plaintext block to `plain[0..16]`, and move the carry to `cipher[0..]`.

The rest of the decrypt side:

- **MAC pass:** the same framing, with a callback that does nothing. Nothing is decrypted or
  written.
- **v3 padding check:** `decrypt_final_block` decrypts `chain`, XORs it with
  `chain_before`, and puts the result in the pending block.
- **Trailer:** `extract_hmac_simple` and `extract_hmac_scattered` read the linear carry, and
  `remaining()` becomes `carry_len`. The messages are unchanged.
- **`RingBuffer64`** becomes unused. Whether to remove it is the owner's call.

## Guardrails

- **Wire format byte-identical.** S01's golden hashes are the check.
- **No early plaintext.** `decrypt_verified` releases no unauthenticated plaintext (EFV
  #1417's rule). The one-pass `decrypt` keeps its documented decrypt-then-verify contract.
- **secure-gate rc.15 discipline,** per `.claude/skills/aescrypt-rs-secure-gate`:
  - Tier 1 access only;
  - every buffer holding plaintext or a key is a `Fixed`;
  - no `Vec`, `BufReader` or `BufWriter` for plaintext.
- **`#![forbid(unsafe_code)]` and MSRV 1.85.** `.github/workflows/msrv.yml` is the CI gate.
- **Issue references:** no fix or close words next to the master's number; use `Refs` only.
